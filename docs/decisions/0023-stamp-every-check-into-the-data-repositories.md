# 0023: 確認した日を毎週データリポジトリに残す

## 状態

承認済み (2026-08-22)。[0020](0020-check-weekly-by-diffing-the-ledger-csv.md) の
「確認日はデータリポジトリに書かない」だけを改める。週次で台帳を取り直すこと・
CSV 同士の突き合わせ・**利用日の据え置き**はそのまま引き継ぐ。

## 文脈

0020 は「データが変わらない週は**どこにもコミットが立たない**」形にした。生成物が
決定的で ([0014](0014-machine-readable-dataset-metadata.md))、利用日は「そのデータを
取り出した日」なので取り出し直していない種別では動かない。年 120 の「確認しただけ」の
コミットが消え、履歴は「いつ何が変わったか」だけになった。

確かめ続けていることは **heritages のサイトの「最終確認」が示す**、とした。渡し先は
サイト側の変数 `LAST_CHECKED_DATE` 1 つで、データリポジトリには何も書かない。

**ところが、データリポジトリの側には手がかりが 1 つも残らない。** 10 個のデータ
リポジトリはそれ自体が配布物で ([0019](0019-distribute-archives-through-releases.md)
の ZIP、clone、生の JSON Lines)、単独で読まれる。最終コミットが 3 週間前のとき、
それが**上流が動いていないのか、週次が落ちて取得できていないのか**を、そのリポジトリ
だけからは判定できない。

- **サイトを見れば分かる、は成り立たない。** clone した人も ZIP を落とした人も
  サイトを見ない。0014 が `meta.json` を中央に 1 枚ではなく各リポジトリのルートへ
  置いた理由 (「リポジトリを 1 つだけ複製した人が正しい出典表記を作れなくなる」) と
  同じ形の問題で、**来歴はデータと一緒に旅する必要がある**
- **Actions の実行履歴は 90 日で消える**うえ、別リポジトリ (クローラー側) にある
- **週次が静かに落ちる形は実際にあった。** 台帳が毎回同じ地域で死んで 1 つも前へ
  進めなかった週がある ([0022](0022-keep-fetching-the-ledger-when-one-area-fails.md))

0020 が嫌ったのは「履歴の大半が確認しただけで埋まる」ことだった。**止まっていることに
気付けない代償の方が高い** — 気付けなければ、古いデータを正しいものとして配り続ける。

## 決定

**各データリポジトリのルートに `status.json` を置き、中身が変わらない週も毎週書いて
push する。**

```json
{
  "schema_version": 1,
  "repo": "historic-sites",
  "checked_date": "2026-08-24",
  "accessed_date": "2026-08-12",
  "changed": false,
  "records": 1854,
  "run_url": "https://github.com/shinyaoguri/heritage-crawler/actions/runs/123456"
}
```

- **日付を 2 つ並べる。** 確認日は「データベースを**見にいった**日」、利用日は
  「そのデータを**取り出した**日」(`meta.json` と同じ値)。2 つが並んで初めて
  「先週も確かめた。中身が古いのは上流が動いていないから」と読める
- **`meta.json` には相乗りさせない。** あれは同じ入力なら同じバイト列になる生成物で
  (0014)、日付を入れると `build-records` (ローカルの全件組み立て) の出力まで実行日で
  揺れる。出典表記が求める利用日と、運用の確認日は意味が違う
- **置き場はルート。** `data/` の下に置くと `meta.json` に無いファイルとして配信側に
  弾かれる ([0021](0021-record-removals-with-evidence.md) の `removed.jsonl` と同じ)
- **コミットを分ける。** 中身が動いたかは `data` / `meta.json` / `removed.jsonl` の
  差分で判定し、「◯◯ に確認 (差分なし)」と「◯◯ の差分を反映」でメッセージを変える。
  中身の変化だけを追う人は `git log -- data meta.json removed.jsonl` で絞れる
- **書くのは週次だけ。** `build-records` は相手先を見にいっていないので書かない。
  実行のたび動く値を差分更新の経路 1 本に閉じ込めることで、全件の組み立て直しは
  決定的なまま保つ
- **heritages への確認日はそのまま渡す。** サイトは 10 リポジトリを束ねて見せる場所
  なので、変数 1 つで足りている (両者は同じ日付になる)

## 影響

- **各データリポジトリに毎週 1 コミットが立つ** (10 × 52 = 年 520)。0020 が消した
  「確認しただけの履歴」が形を変えて戻る。**ファイルとコミットメッセージで区別できる**
  ぶんだけ、月次の頃より読みやすい
- **データリポジトリ 1 つだけを見て、静かなのか止まっているのかが分かる。** 確認日が
  古ければ取得できていない。確認日が新しくて利用日が古ければ上流が動いていない
- **配信側の検査は変わらない。** heritages が突き合わせるのは `data/` 配下だけなので、
  ルートに増えた 1 枚は素通りする (`removed.jsonl` と同じ)
- 週次のジョブが `update-records` より手前で落ちた週は、`status.json` も動かない。
  **確認日が進まないこと自体が、止まっていることの印**になる
- 将来 heritages が各リポジトリの `status.json` を読めば、`LAST_CHECKED_DATE` 変数は
  畳める。今回は触らない (サイト側の変更になるため)
- 配布する ZIP に 1 ファイル増える
