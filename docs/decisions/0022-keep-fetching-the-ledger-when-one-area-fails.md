# 0022: 台帳の取得は 1 地域が取れなくても止めない

## 状態

承認済み (2026-08-21)。
[0011](0011-back-off-to-1-rps-and-detect-error-pages.md) が詳細ページに定めた
「200 で返るエラーページを失敗として扱い、記録して次へ進む」を**台帳の取得へも広げる**。
レートの上限 (1 req/s) も、失敗を記録して後から拾い直す形も変えない。

## 文脈

2026-08-16 03:00 JST の週次実行
([run #4](https://github.com/shinyaoguri/heritage-crawler/actions/runs/31965106509))
が `fetch-ledger` で失敗し、その週の更新がまるごと飛んだ
([#53](https://github.com/shinyaoguri/heritage-crawler/issues/53))。

101 の全 51 地域と 102 の愛知県までは正常に取れていた (リクエスト間隔は 3〜5 秒で、
上限の 1 req/s を守っている)。**102 × 三重県**の検索応答で件数表示 (`td.searchnum`)
が読めず、そこで実行が止まった。同じ検索を 2026-08-21 に手元から引くと 26 件が
正常に返る。サイトの構成変更ではなく、相手側の一時的な不調である。

失敗そのものより、**繰り返しても前へ進まなかった**ことが問題だった。

| 時刻 (UTC) | 起きたこと |
|---|---|
| 18:46 | 102 × 三重県 で読めない応答。トークンを取り直して即再試行 → 同じ。実行が終了 |
| 18:51 | `retry.sh` の 2 回目。取得済みを飛ばした先頭は**また三重県** → 同じ |
| 18:56 | 3 回目 → 同じ。19 分かけて 1 地域も進まず、以降の 20 県 + 103 + 401 は手つかず |

原因は 2 つ重なっている。

- **待たずに 1 度しか取り直さない。** `ledger.search` の再試行はトークンの失効を
  想定した作りだった。読めない応答は 200 で返るので HTTP クライアント側の再試行
  (5xx とタイムアウトが対象) は働かず、相手の不調には何も効いていない
- **1 地域の失敗が実行全体を止める。** `fetch_ledgers` は例外をそのまま投げていた。
  取得済みを飛ばして再開する作りは、**止まった地点が毎回そのまま先頭になる**ことを
  意味する。相手の不調が続く限り、再試行は同じ石に躓き続ける

詳細ページの取得 (`fetch_details`) は 0011 の時点で「1 件失敗しても止めず、記録して
次へ進み、`--retry-failed` で拾い直す」形になっている。台帳だけが取り残されていた。

## 決定

- **1 つ取れなくても止めない。** `fetch_ledgers` は取得の失敗
  (`FetchError` / `LedgerError` / `ParseError`) を記録して次の地域へ進み、結果を
  `LedgerRun` (取得数・取れなかったものの一覧・打ち切り理由) で返す。取れたぶんは
  キャッシュに入るので、次の回に取りに行くのは**残りだけ**になる
- **取れなかったものがあれば `fetch-ledger` は 1 を返す。** 週次はこの終了コードで
  `retry.sh` の次の回を呼ぶ。取れたぶんの報告 (`report-ledger` と同じ表) は
  失敗があっても印字する — どこまで進んだかが次の回の入力になる
- **全国件数の失敗も同じ扱い。** キャッシュを上書きしないだけで地域の取得は続ける。
  全国件数は毎回数え直すので次の回に拾える
- **読めない応答には待ちを挟んで 3 回まで粘る** (2 秒・4 秒)。待ち時間は
  `http.RETRY_BACKOFF` と同じ考え方で、**レートの間隔からは導かない**
  ([0010](0010-rate-limit-by-request-start.md))
- **5 件続けて失敗したら打ち切る。** 相手が落ちているときに 204 地域を叩き続けない。
  1 地域 = 検索 + CSV の 2 リクエストと重いので、詳細ページの打ち切り (10 件) より
  早く止める
- **読めなかった応答は、諦めるときに大きさと先頭を記録に残す。** 今回、壊れた応答の
  実物がどこにも残らず、エラーページ (0011) と構成変更を切り分けられなかった

## 影響

- 相手が数分不調でも、その週の更新は通るようになる。1 回目で不調な地域以外を
  取り切り、`retry.sh` の次の回が残りだけを試すため、**相手への総リクエスト数は
  増えない** (むしろ同じ地域を 3 回叩いていた今までより減る)
- **取れなかった地域があるまま先へ進むことはない。** 終了コードが 1 なので、週次は
  2 段目 (詳細の取り直し) にも push にも進まず、データリポジトリは前回のまま残る。
  網羅性の判定 (`summarize` / `looks_complete`) が未取得の地域を完了扱いしないのも
  従来どおりで、**消えた指定を誤って落とす経路は増えない**
- 相手が長く不調な週は、これまでどおり失敗して Issue が立つ。**変わったのは
  「1 地域の不調で全体を失う」ことが無くなった点だけ**で、粘る量そのものは
  `retry.sh` の 3 回 × 5 分のまま増やしていない
- 打ち切りの閾値 (5) は実測ではなく見積もり。相手が本当に落ちている週に早すぎる /
  遅すぎるようなら、実行ログを見て調整する
