# 0006: 初回の全件取得はローカルで行い、以降の差分更新は GitHub Actions で回す

## 状態

承認済み (2026-08-11)

## 文脈

2026-08-11 に取得規模を実測した。指定単位と棟単位の比は分類によって異なる。

| 分類 | 指定数 | 棟への展開 | 推定棟数 |
|---|---|---|---|
| 101 登録有形文化財（建造物） | 14,748 | 1:1 (北海道 155→155、東京 485→485) | 14,748 |
| 102 国宝・重要文化財（建造物） | 2,633 | 1:2.5 (北海道 34→85) | 約 6,600 |
| 103 重要伝統的建造物群保存地区 | 126 | 地区単位 | 126 |

- 詳細ページの取得対象は**合計およそ 21,500 件**
- CSV 側は 3 分類 × 47 都道府県 = 141 リクエストで、数分で終わる
- 1 秒 1 リクエストなら詳細ページの取得に**約 6.0 時間**かかる
- 詳細ページの HTML は 41〜55 KB。全件の生 HTML はおよそ **1 GB**

実行場所の候補ごとの制約は次のとおり。

- **GitHub Actions**: GitHub ホストランナーの**ジョブ上限がちょうど 6 時間**で、
  単一ジョブでの全件取得は綱渡りになる。Free プランの private リポは
  月 2,000 分の無料枠があり、全件を回しても約 360 分 (18%) で収まるため、
  費用が障害になるわけではない。ただしデータセンター IP からの
  2 万件アクセスが通るかは未検証で、CloudFront 配下のため WAF の挙動が読めない
- **ローカル**: 実行時間の上限が無く、レートを緩めて長時間かけられる。
  1 GB のキャッシュを置くのも容易。curl での取得実績がある (ADR 0002 の調査)
- **クラウドサーバ**: 月に数分から数時間しか動かない処理のために常時稼働の
  サーバを持つと、費用より OS 更新や監視といった管理の手間が見合わない

## 決定

- **初回の全件取得はローカルで行う。** 6 時間級の処理は初回ほど中断と再開を
  繰り返すため、実行時間の上限と無料枠を気にせず、レートを自由に緩められる
  環境が要る。相手先から見た IP が一般回線である点でも穏当
- **以降の差分更新は GitHub Actions の月次スケジュールで回す。** 差分は短時間で
  終わり、実行記録が自動で残り、手元マシンの状態に依存しなくなる
- **クラウドサーバは使わない**

実行場所は後から変えられるようにする。そのためにクローラーは次を満たす。

1. **取得と解析を分離し、生 HTML をキャッシュする** (最重要)
2. 中断・再開できる。状態をファイルに持ち、一度で完走する前提を置かない
3. レートと並列度を設定で変えられる
4. 出力先ディレクトリをパラメータで受ける (データリポは別: ADR 0001)

## 影響

- **生 HTML のキャッシュは必須**。パース仕様を変えるたびに 21,500 ページを
  取り直すのは相手先に対して失礼であり、毎回 6 時間かかっては開発が進まない。
  gzip で保存すれば 1 GB が 100 MB 前後に収まる
- キャッシュはリポジトリにコミットしない (1 GB はリポジトリに載せる規模ではない)。
  リポジトリに入れるのは抽出後の JSON Lines (20〜40 MB 規模の見込み)
- Actions で都道府県マトリクスを使う場合は **`max-parallel: 1` を必ず付ける**。
  付けないと 47 都道府県が同時に走り、ADR 0002 で決めた逐次アクセスの方針に反する
- Actions からデータリポジトリへ push するには PAT か GitHub App の用意が要る
- Actions の IP で取得できるかは、**分類 103 (126 件) で先に疎通確認する**。
  数分で終わり、最小の負荷で確かめられる
