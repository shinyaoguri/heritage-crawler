# 0021: 削除された指定は証拠つきで `removed.jsonl` に残す

## 状態

承認済み (2026-08-16)。[0018](0018-detect-monthly-changes-with-the-ledger-and-a-rotation.md) /
[0020](0020-check-weekly-by-diffing-the-ledger-csv.md) が決めた「台帳から消えたキーは
出力から落とす」に、**記録**と**検証**を足す。落とすこと自体は変えない。

## 文脈

差分更新は台帳から消えたキーを指定解除として出力から落とす (`update.plan_update`)。
**落としたことの記録がどこにも残らない。**

| 残っているもの | 寿命 | 機械可読 |
|---|---|---|
| Actions の実行ログ (`format_plan` が 10 件まで名指し) | 90 日 | × |
| データリポジトリの git 履歴 (行を消したコミット) | 恒久 | △ (10 リポジトリを横断して `git log -S`) |

「いま何が解除されているか」を問う手段が無い。指定解除は焼失・取り壊し・移築に伴って
起こる、このデータで最も知りたい出来事の一つで、現存リストと同じだけの価値がある。
あわせて、誤って消したものを名指しで拾い直せる保険にもなる。

### 「削除された」と言えるのか

記録を作る前に、何をもって削除と言うのかを詰めた。段階は 3 つある。

1. **手元から消えた** — 台帳 CSV に現れない。これは*不在*という消極的な証拠で、
   自分の取りこぼしと区別がつかない。0018 / 0020 の実装はここで止まっている
2. **データベースから消えた** — 下記の 2 系統の証拠で言える
3. **指定が解除された** — 2 でも言い切れない (格上げがあるため。後述)

**証拠は 2 系統ある。**

- **集計レベル** — 全国件数と手元のキーの異なり数が一致していること
  (`CategorySummary.looks_complete`)。取りこぼしがあれば手元が全国件数より少なくなるので、
  **一致している週の不在は取りこぼしではありえない**。0018 から実装済みで、想定より強い保証
- **個別レベル** — その 1 件の詳細ページを引く。**いまの設計には無い。**
  `plan_update` が `Target` を作るのは台帳の行からだけで、消えたキーは一度も存在確認
  されないまま落ちている

| 分類 | 集計レベル | 個別レベル | 現状 |
|---|---|---|---|
| 101 / 103 / 401 | ○ 成立する | ○ 足せる | 二重の証拠になる |
| **102** | **× 成立しない** (棟単位なので件数表示の差しか見られない) | ○ 足せる | **弱い根拠だけで消している** |

102 の `looks_complete` は `difference >= 0`、つまり「地域をまたぐ重複がある」ことしか
言えず、**取りこぼしと重複が相殺していても真になる** (#28 で 401 が踏んだ罠と同じ)。
にもかかわらず 102 は落とす側に入る。**詳細ページの検査は 102 にとって唯一の個別証拠。**

### 実測 (2026-08-16)

存在しない `管理対象ID` で詳細ページを引くと、はっきり「無い」と答える。

| リクエスト | 応答 |
|---|---|
| `102/00003904` (実在) | 56,632 バイトの詳細ページ |
| `102/99999999` (不在) | 3,008 バイト・本文に「必要な情報が足りません」 |

**既存の `detail.rejected()` がそのまま検出する** (`ERROR_PAGE_MARKERS` に入っている)。
[0011](0011-back-off-to-1-rps-and-detect-error-pages.md) でエラーページ対策として作った
判定が、そのまま削除の直接的な証拠を取る道具になる。

### それでも残る穴が 2 つ

**1. エラーページの多義性。** 「必要な情報が足りません」は、
[0011](0011-back-off-to-1-rps-and-detect-error-pages.md) の実測では **4 req/s で叩いた
ときに応答の 15% がこれになった**ときの目印でもある。この文言は「そのレコードは無い」と
「いま混んでいて答えられない」の**両方**を意味する。素朴に引くと、混んだ時間帯に当たった
1 件を削除と記録しかねない。

**2. 格上げは詳細ページでは区別できない。** 台帳ID は分類コードそのもの。**登録有形
文化財 (101) が重要文化財 (102) に指定されると登録は抹消され、キーの台帳ID が変わって
別のレコードになる。** 手元からは「101 から 1 件消えて 102 に 1 件現れた」と見えるが、
これは削除ではなく格上げで、文化財としてはむしろ価値が公認された出来事。純粋な指定解除
(焼失・取り壊し) より頻度が高い可能性すらある。101 側の詳細ページは正しく消えるので、
詳細ページの検査では見分けられない。

## 決定

**各データリポジトリのルートに `removed.jsonl` を 1 枚置き、判定ではなく証拠を書く。**

- **置き場はデータリポジトリのルート。** `meta.json` と同じ理屈で
  ([0014](0014-machine-readable-dataset-metadata.md))、データに付く情報はデータと
  一緒に旅する必要がある。リポジトリを 1 つだけ複製した人にも見える。件数は年に
  数件〜数十件なので都道府県では分けない
- **`data/` の下には置かない。** 閲覧サイトが読むのも
  ([0015](0015-single-cross-type-site-on-pages.md))、配布物に入るのも
  ([0019](0019-distribute-archives-through-releases.md))、配信前の検査が見るのも
  `data/*.jsonl` だけ。ルートに置けば `code4heritage/heritages` は自動的に無視するので、
  **向こうに手を入れずに済む**。逆に `data/` へ置くと「`meta.json` に無いのに置かれて
  いるファイル」として配信が止まる
- **中身は最後に観測したレコード全体**に、下記のメタを足したもの。名称も所在地も座標も
  無い削除リストは事実上「番号の列」でしかない
- **状態型にする。** `removed.jsonl` は「いま消えているもの」の一覧で、復活したら行が
  消える。**誤検出が「解除された文化財」として固定されない**のが要点。「消えて戻った」
  経緯は git 履歴とリリースノート ([0019](0019-distribute-archives-through-releases.md))
  が持つ
- 並びは `(台帳ID, 管理対象ID)`。**生成物は決定的なまま保つ**
  ([0014](0014-machine-readable-dataset-metadata.md))

### 判定ではなく証拠を書く

確実には言い切れない穴が残る以上、結論を 1 語に潰さない。**読む側が自分の基準を
当てられるようにする** — 確実でないものを確実だと書かずに済む。

```json
{
  "ledger_id": "101", "managed_id": "00012345", "name": "…",
  "last_seen_date": "2026-08-10",
  "missing_since": "2026-08-17",
  "evidence": {
    "absent_from_ledger": true,
    "category_complete": true,
    "detail_page": "gone",
    "matched_elsewhere": null
  },
  "conclusion": "delisted"
}
```

**日付は観測日であって告示日ではない。** データベースは解除の告示日を持たず、行が消える
だけなので、`removed_date` と書くと官報の日付だと誤読される。

| キー | 意味 |
|---|---|
| `last_seen_date` | 最後に台帳で見た日 (前回の `meta.json` の利用日から出る実測値) |
| `missing_since` | 台帳から消えているのを最初に観測した日 |

`conclusion` の語彙は 5 つ。

| 値 | 意味 |
|---|---|
| `delisted` | 台帳から消え、網羅性も確かめられ、詳細ページも消えた。**最も強い** |
| `unlisted` | 台帳から消えたが詳細ページは生きている (検索対象から外れただけ) |
| `reclassified` | 別の分類に同じものが現れた (101 → 102 の格上げなど)。**削除ではない** |
| `rerouted` | 台帳にはあるが同じ分類の中で振り分け先が変わった (401 の種別変更、102 の国宝・重文区分の変更)。そのリポジトリからは消えるので載せる |
| `unverified` | 網羅性も詳細ページも確かめられなかった |

### 削除候補は詳細ページで存在を確かめる

**対照群を置く。** 同じ回に**実在すると分かっているキーを 1 件引き**、それが正常な詳細
ページを返すことを確かめる。返せばその時点で相手は正常に答えているので、隣で返った
「必要な情報が足りません」は本物だと言える。**エラーページの多義性はこれで断ち切る** —
1 req/s を守っていれば過負荷由来は起きない ([0011](0011-back-off-to-1-rps-and-detect-error-pages.md))
が、それは統計であって個別の 1 件の保証にはならない。対照群が正常でなければ、その回は
`unverified` にして落とさない。

**格上げは名称 + 所在地 + 緯度経度の照合で見分ける。** 同じ回の削除候補と新規候補を
突き合わせ、一致すれば `reclassified`。告示のタイミングがずれて別の週になる可能性は
残るが、大半は拾える。

**`plan.retained` は載せない。** あれは「その週その分類の取得が完全だと言い切れず、
消えた行を指定解除と断じられない」という一時的な状態で、平時は 0 件、取得が転んだ週にだけ
現れて翌週消える。削除されていない行を削除リストに書くと名前と実態がずれるうえ、恒久
ファイルが毎週揺れて決定性のノイズになる。

## 影響

- **相手先への追加は週に数件〜数十件 + 対照群 1 件。** 1 req/s でも数十秒で、週次全体
  (約 45 分) から見れば誤差
- **102 の削除判定が集計ゲート頼みでなくなる。** これが最大の効果 — 102 はキーの異なり数を
  全国件数と直接比べられない唯一の分類で、いまは相殺で隠れた取りこぼしを指定解除と
  読み違えうる。あわせて `looks_complete` というゲート 1 本への依存自体が下がる
- **`removed.jsonl` はキャッシュから再現できない履歴情報**になる。出力はこれまで
  「キャッシュ + 前回の出力」から決定的に作られてきたが、この 1 枚だけは違う。
  **`build-records` (全件再組み立て) でも既存の `removed.jsonl` を読んで素通しする** —
  この約束が無いと、スキーマ変更のたびに静かに失われる
  ([0006](0006-run-initial-crawl-locally-updates-on-actions.md) の分担で、全件再組み立ては
  ローカルに残っている)
- **`meta.json` には削除件数を載せない。** 載せると `build-records` が
  `removed.jsonl` を読まない限り件数がドリフトし、上の「触らない」約束と両立しない。
  件数はファイル自身が持っていれば足りる
- **`code4heritage/heritages` は変更しない。** ZIP にもサイトにも出ない。ただし配布物は
  「展開するとそのデータリポジトリの中身そのものになる」ことを意図しているので
  ([0019](0019-distribute-archives-through-releases.md))、後から入れたくなる可能性はある。
  そのときは向こうの `EXTRA_FILENAMES` に 1 行足すだけで済む
- **データが変わらない週にコミットが立たない性質は保たれる**
  ([0020](0020-check-weekly-by-diffing-the-ledger-csv.md))。削除が無い週は
  `removed.jsonl` も 1 バイトも変わらない
- **まだ分かっていないことが 1 つ残る。** 実測したのは*存在しない ID* の挙動であって、
  *実際に解除されたレコード*ではない。解除された文化財がデータベースから本当に消えるのか、
  検索対象外になるだけで詳細ページは残るのかは、実例が出るまで分からない。**どちらでも
  検査には意味がある** — 消えるなら強い証拠になり、残るなら「解除されても詳細ページは
  残る」という事実自体がこのデータベースについての発見になる。`unlisted` を語彙に
  入れてあるのはそのため
