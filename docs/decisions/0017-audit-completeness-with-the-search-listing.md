# 0017: 網羅性は検索結果一覧で確かめ、地域で引けない指定は一覧から回収する

## 状態

一部置換 (2026-08-12) — **「棟に展開される分類は対象外」と「回収で地域欄を埋める」を
[0026](0026-audit-with-the-listing-where-its-keys-are-ledger-keys.md) が改めた**
(2026-08-24)。弾く条件は展開の有無ではなく「一覧のキーが台帳のキーに載るか」で、
201 はこれを満たす。ほかはそのまま生きている。

## 文脈

台帳は分類 × 地域で取る ([0002](0002-two-stage-fetch-csv-then-detail.md))。地域は
検索フォームの `seat_pref` に**格納値の完全一致**で送るので、データ側の都道府県が
その形になっていない指定は引けない。実測で 3 通りある。

| データ側の都道府県 | 引けるか |
|---|---|
| `２県以上` / `地域を定めない` | 引ける (分割軸に入れてある。401 に 95 行) |
| 未正規化の値 (`98` / `1`) | 引ける (`catalog.IRREGULAR_AREAS` でその値を直接送る) |
| **空** | **引けない** |

空だけが違うのは、`seat_pref` に空を送ると絞り込みが外れて全国検索になるためで、
`IRREGULAR_AREAS` の手が使えない。401 の「智頭往来 志戸坂峠越」がこれに当たり、
全国 3,281 件に対して手元が 3,280 件だった (Issue #28)。

代わりに全国の CSV を取れれば済むが、**2,000 件を超える CSV 出力は 504 になる**
(2026-08-12 に 401 で再確認。60 秒のタイムアウトを 3 回とも使い切る)。件数表示
どうしの引き算でも駄目で、地域をまたぐ重複と取りこぼしが相殺して消える (#33 で
キーの異なり数に変えたが、それは「何件足りないか」までしか分からない)。

一方、**検索結果一覧 (HTML) は地域で絞らずに最後まで辿れる**。1 行 = 1 **指定**で、
`(台帳ID, 管理対象ID)`・名称・都道府県欄に加えて、地図表示ボタンが
`mapChange('401', '2', 43.45322226000000, 144.10229501000000)` の形で**緯度経度**を
持つ。実データで CSV の緯度経度と完全一致することを確かめた。そして
[0008](0008-normalize-schema-detail-page-wins.md) のとおり、**CSV から採っている
のは緯度経度だけ**で、残りは詳細ページから採っている。

ページ送りの値は素直ではない。番号は `page_no` ではなく **`pageNumber`**
(`page_no` は常に 1 のまま送られる飾りで、変えても 1 ページ目が返る)。表示件数は
`pageSize` で 20 / 50 / 100 から選べる。

## 決定

- **網羅性の最終確認は検索結果一覧の全ページ収集で行う。** 集めたキーの集合を
  手元の CSV のキーの集合と突き合わせ、**取りこぼしを 1 件ずつ名指しする**。
  地域欄も一緒に出す — 空なら原因がその場で分かる
- **棟に展開される分類 (102) は対象外。** 一覧は指定単位・CSV は棟単位で、複数棟の
  指定は詳細ページへ直接リンクされない (棟一覧のモーダルになる)。
  `Category.expands_to_buildings` で弾き、通信する前に断る
  — **弾く条件は [0026](0026-audit-with-the-listing-where-its-keys-are-ledger-keys.md)
  が `audits_with_listing` に改めた。** 102 が対象外なのは変わらないが、同じフラグで
  巻き添えになっていた 201 は突き合わせられる
- **取りこぼした指定は一覧の行から台帳の CSV として組み立て直す** (回収)。
  埋めるのは名称・都道府県欄・緯度経度だけで、あとは空。読む側から見れば地域別
  CSV と同じ 18 列なので、`fetch-detail` も `build-records` も通常どおり流れる
  — **都道府県欄は
  [0026](0026-audit-with-the-listing-where-its-keys-are-ledger-keys.md) が外した。**
  一覧の列見出しは全分類で「都道府県」だが CSV の 12 列目の意味は分類で変わるため
- **回収 CSV は毎回まるごと書き直す。** 元データの都道府県が埋まれば地域別で
  引けるようになり、回収ぶんは消えるべきものだから (追記すると古い行が残る)
- **ページ送りと表示件数の値は推測して組み立てず、応答の中のフォームの hidden 値を
  そのまま送る** ([0002](0002-two-stage-fetch-csv-then-detail.md) と同じ理由)。
  表示件数は毎回 100 にする — 20 のままだと相手へのリクエストが 5 倍になる
- **検査と修復は分ける。** 既定は報告だけで、台帳へ書くのは `--recover` を
  付けたときに限る。取りこぼしが残っていれば異常終了して、気付かずに次の工程へ
  進まないようにする

## 影響

- リクエスト数は `ceil(指定件数 / 100) + 2`。101 = 150 / 103 = 4 / 401 = 35 で、
  台帳取得 (204 リクエスト) と同じ桁に収まる。月次更新
  ([0006](0006-run-initial-crawl-locally-updates-on-actions.md)) に足しても
  レート上限 1 req/s のまま数分で終わる
- 102 の網羅性は従来どおり件数表示の差でしか見られない。棟単位で全国と比べる術は
  無いままで、これは一覧の作りが変わらない限り解けない
- 相手のマークアップに依存する箇所が増える。列は見出しの語 (`都道府県`) から
  colspan を数えて位置を出し、行が 1 つも読めなければ失敗させる — 静かに
  「取りこぼし 0 件」と報告しないため
- 回収した行は都道府県が空のままなので、出力先は
  `record.resolve_location` が所在地から決める ([0004](0004-output-jsonl-per-prefecture.md)
  のファイル分割)。「所在地から決めた」件数として `build-records` の報告に出る
- 元データが直れば回収は自動的に 0 件になり、回収 CSV も消える。この決定を
  取り消す必要は無い (検査は残る)
