# 0029: データリポジトリへの push は 1 つ押せなくても止めない

## 状態

採用 (2026-09-22)。

[0022](0022-keep-fetching-the-ledger-when-one-area-fails.md) が台帳の取得に定めた
「1 つ取れなくても記録して次へ進む」を、**週次の最後の 1 区間 (push) へ広げる**もの。
取得層 (0011 / 0022) は既にこの形で、押す側だけが取り残されていた。

## 文脈

2026-09-20 の週次実行
([run 35536131615](https://github.com/shinyaoguri/heritage-crawler/actions/runs/35536131615))
が push で失敗し、その週の更新がほぼまるごと飛んだ
([Issue #98](https://github.com/shinyaoguri/heritage-crawler/issues/98))。

**取得は完走している。** 1 時間かけて台帳を取り直し、差分を組み立て、26 リポジトリの
1 番目を押し終えたあと、2 番目で GitHub が push を弾いた。

```
remote: fatal error in commit_refs
 ! [remote rejected] main -> main (failure)
error: failed to push some refs to 'https://github.com/code4heritage/national-treasures.git'
```

`commit_refs` のエラーは GitHub 側の一時的な障害で、こちらの入力に原因は無い
(同じ内容が前週も翌週も押せている)。押しはじめから弾かれるまで 20 秒。

問題は失敗そのものではなく、**20 秒の不調で 24 リポジトリが試みられもしなかった**
こと。`scripts/push-data-repos.sh` は `set -e` で走っており、最初の `git push` の
失敗がそのままスクリプトの終了になっていた。

| リポジトリ (`catalog.TARGET_DATASETS` の順) | 結果 |
|---|---|
| 1 番目 registered-tangible-cultural-properties | 押せた (確認日 2026-09-21) |
| 2 番目 national-treasures | **弾かれた** |
| 3〜26 番目 | **試みてもいない** (確認日 2026-09-14 のまま) |

押す相手は 26 個の**別々のリポジトリ**で、互いに依存しない。1 つが押せないことは
ほかの 25 が押せない理由にならない。2 段目までの 1 時間ぶんの成果を捨てる理由にも。

**失敗 Issue の本文も実態とずれていた。** 書き分けが「押したあとに落ちた」と
「押す前に落ちた」の 2 通りしかなく、自動で立った #98 は一部が更新済みなのに
「データリポジトリは前回のまま」と書いていた。**読み手が状態を誤認する** —
2026-08-22 に「一律に前回のままと書く」をやめた
([0023](0023-stamp-every-check-into-the-data-repositories.md)) のと同じ間違いが、
新しい形で残っていた。

## 決定

- **1 つ押せなくても止めない。** `push-data-repos.sh` は `git add` / `commit` /
  `push` それぞれの失敗を記録して次のリポジトリへ進む。押せたぶんは押せたまま残る
- **押すところだけを繰り返す。** 一時的な弾かれ方は数秒〜数十秒で明けるので、
  同じ `scripts/retry.sh` で 3 回 × 15 秒粘る。**commit からやり直さない** —
  同じ内容のコミットが試行のぶんだけ積み上がる。回数と待ちは
  `PUSH_RETRY_ATTEMPTS` / `PUSH_RETRY_DELAY` で上書きできる (テストは 0 秒で回す)
- **数えるのは押せたぶんだけ。** 手元で commit しただけのものを `changed` /
  `checked` に入れない。押せなかった数は `failed` として出力にもまとめにも出す
- **1 つでも押せなければ 1 を返す。** ジョブは赤くなり、失敗 Issue は従来どおり
  立つ。粘ったうえで駄目だったことを緑にはしない
- **失敗 Issue の本文は 3 通り。** 全部押した / **一部だけ押せた** / 押す前に
  落ちた。一部だけの回は押せた数と押せなかった数を書き、翌週の実行が押し直すこと、
  待たずに揃えるなら手で起こせることまで書く
- **テストは実際の `git push` で確かめる** (`scripts/test-push-data-repos.sh`)。
  押し先は手元の bare リポジトリで、弾かれ方は `pre-receive` フックで作る —
  相手が弾いたときと同じ経路で `remote rejected` になる。常に弾くリポジトリを
  一覧の**先頭**に置き (2026-09-20 と同じ並び)、後続が押せることを見る

## 影響

- 相手が数十秒不調でも、その週の更新はほぼ通る。1 リポジトリが落ちても残り 25 は
  押され、**取得の 1 時間が丸ごと無駄になることは無くなった**
- **押せなかったリポジトリは確認日が古いまま残る。** これは欠陥ではなく設計どおりで、
  サイトは確認日の**一番古い日**を採るので (`docs/pipeline.md`)、一部が取り残された
  週に「全部確かめた」と表示されることはない ([0028](0028-read-the-checked-date-from-the-data.md))
- **押し直しは翌週の実行に任せてよい。** 次の回はデータリポジトリを clone し直して
  前回の状態を読むので ([0018](0018-detect-monthly-changes-with-the-ledger-and-a-rotation.md))、
  押せなかったぶんは**その週の差分として自然に
  押し直される**。手元に残した commit を持ち回る仕組みは要らない
- **部分的に押された状態は前から起こりうる。** ジョブの打ち切りやトークンの失効でも
  同じ状態になるため、`concurrency` は走っている回を殺さない設定のままにしてある。
  変わったのは、その状態が**失敗 Issue から読める**ようになった点
- 再試行の回数 (3) と待ち (15 秒) は見積もり。相手の不調がもっと長い週があるなら
  実行ログを見て調整する。26 リポジトリが全滅しても足されるのは 13 分ほどで、
  ジョブの上限 (180 分) には遠い
- **押す相手が増えても変わらない。** 分類や出力先が増えて一覧が伸びても、
  1 つの不調が全体を落とさない性質は保たれる
