# 0030: データベース側の不具合は、行の印と `source-issues.jsonl` で名指しする

## 状態

採用 (2026-09-23)。

[0011](0011-back-off-to-1-rps-and-detect-error-pages.md) は「200 で返るエラーページを
失敗として扱う」と決めた。こちらのレートが原因の失敗の扱いである。本 ADR は、
**相手のサーバそのものが壊れている**ときの扱いを足す。
記録の置き方は [0021](0021-record-removals-with-evidence.md) の `removed.jsonl` に揃える。

## 文脈

`901/00000024` (佐渡島の金山) の詳細ページが、1 か月にわたって HTTP 500 を返し続けた
([Issue #107](https://github.com/shinyaoguri/heritage-crawler/issues/107))。
全 19 分類で、ここだけが全国件数と一致しなかった (指定件数 21 に対して取得 20)。

**原因は相手側だった** (2026-09-23 実測)。

| リクエスト | 応答 |
|---|---|
| `901/00000024` | **500・8.7 KB。** 主情報と本文側の解説文までは描かれている。「構成資産」の一覧を描く途中で途切れ、その後ろにエラー画面 (`location.href='/bsys/error'`) の HTML がつながっている |
| `901/00000023` (存在しない ID) | 500・2.6 KB。エラー画面だけ |
| `901/11` (石見銀山) | 200。同じ位置に、構成資産 (911) とそれが属する指定へのリンクが並ぶ |

検索結果一覧のリンクも同じ URL だった。セッション Cookie の有無でも変わらないので、
URL の組み立て ([0024](0024-record-carries-its-category-code.md)) の誤りではない。
佐渡島の金山は 21 件の中で最も新しい登録 (2024 年) で、構成資産の紐付けが相手の
データベースで欠けていると考えられる。

**いまの作りでは、壊れていることがどこにも残らなかった。**

- 失敗は週次のログに WARNING が 1 行出るだけだった。1 か月、誰も気付かなかった
- 台帳にあって出力に無いので、毎週「新規」として叩かれ、毎週失敗していた。
  相手が直しても、それに気付く仕組みが無かった
- 取れない 1 件が「詳細が未取得」に数えられた。そのせいで、0 件になった県ファイルの
  掃除 (#57) が毎週止まっていた
- 取り直し (巡回・台帳の変化) に失敗した行は、前回の行が黙って使われた。
  古いまま使っていることも、どこにも残らなかった

## 決定

**不具合を 3 つの場所に残す。** 取れたところは捨てずに採り、欠けていることを明示する。

### 1. 取得層: 途中まで描かれたページを残す

- 5xx の本文に、主情報の終わり (`<!-- heritage_detail END -->`) とエラー画面への
  切り替え (`/bsys/error`) が**両方**あれば、途中まで描かれたページとみなす。
  本文をキャッシュに保存し、`DetailEntry.issue = "truncated"` の印を付ける
  (`detail.truncated` / `TRUNCATED_MARKERS`)
- **連続失敗には数える。** 相手がエラーを返していることに変わりはない。広い範囲で
  途中切れが起き始めたら、今までどおり打ち切る
- 「存在しない ID」の 500 は目印を片方しか持たないので、今までどおり失敗になる

### 2. データ: 行に印、リポジトリのルートに一覧

- **行の印。** 途中まで描かれたページから組み立てた行には `source_issue` を付ける
  (値は `"詳細ページの一部が欠けている"`)
  - 値を文字列 1 つにし、`meta.json` の facets にも載せる。閲覧サイトは facets から
    絞り込みを作るので、heritages に手を入れずに「不具合のあるものだけ」を選べる
  - 切れた位置より後ろ (関連情報・附指定などの一覧・写真) は取れていない。
    そのため `has_*` のように「無い」と断定する値は書かない
  - **前回の完全な行があれば上書きしない。** 古くても揃った行を残し、「古い」と名指しする
- **ルートの一覧 `source-issues.jsonl`。** `removed.jsonl` と同じく状態型にする。
  並ぶのは「いま問題があるもの」だけで、直れば行は消え、0 件ならファイルごと消える

  | `kind` | 意味 | 行は `data/` に |
  |---|---|---|
  | `truncated` | 途中まで描かれたページから行を作った | ある (印付き) |
  | `stale` | 取り直しに失敗し、前回の行をそのまま使っている | ある (印なし。中身は前回取れたもの) |
  | `unavailable` | 一度も取れていない | 無い |

  - `first_seen` は問題を最初に観測した日で、**キーだけで引き継ぐ**。`truncated` と
    `stale` を行き来しても、壊れ始めた日は変わらない
  - `unavailable` を書くのは、振り分けが種別に依存しない分類だけ。102 や 401 は
    詳細ページを読むまで書き先が決まらないので、報告にだけ出す
  - 週ごとに揺れる値 (エラーの文言など) は載せない

### 3. 処理: 毎週確かめ直し、報告に上げる

- 一覧に載ったキーと印の付いた行は、`Reason.RECHECK` で**毎週取り直す**。
  問題は 1 件につき毎週 1 リクエストなので、負荷は無視できる。相手が直せば、
  その週のうちに印と一覧から外れる
- `update-records` の報告に「データベース側の不具合」の節を置き、全件を名指しする。
  週次の Step Summary にそのまま出る。**Issue は立てない**。データは正しく扱えていて、
  人の対応が要る失敗ではない。毎週立てるとノイズにもなる

### 採らなかった案

- **放置する。** 直ったことに誰も気付かず、全国件数とのずれが恒久的な見た目になる
- **検索結果一覧の行からレコードを作る** ([0017](0017-audit-completeness-with-the-search-listing.md))。
  一覧には名称と地域しか無い (佐渡の行は緯度経度も空)。途中まで描かれた本文の方が、
  主情報と解説文まで揃っていて多くを持つ
- **途中切れで前回の行を上書きする。** 相手が広い範囲で途中切れを返すようになると、
  揃った行が欠けた行へ次々と置き換わる
- **`build-records` でも一覧を書く。** `stale` と `first_seen` は前回の出力が無いと
  再現できず、全件を組み立て直すたびに記録が静かに失われる。`removed.jsonl` を
  触らないのと同じ理由 ([0021](0021-record-removals-with-evidence.md))。行の印は
  キャッシュから決まるので、`build-records` でも付く

## 影響

- 佐渡島の金山は、欠けていることを示す印付きで `world-heritage-sites` に入る。
  901 の取得件数は全国件数に揃う。`source-issues.jsonl` に 1 行載り、相手が直した週に消える
- 詳細を取りこぼした実行では 0 件の県ファイルを消さない (#57)。佐渡が組み立てられる
  ことで取りこぼしが無くなり、この掃除が毎週止まる状態は解消する
- **不具合を確かめる場所は 3 つ。** 各データリポジトリの `source-issues.jsonl`・
  閲覧サイトの「データベース側の不具合」の絞り込み・週次の Step Summary
- 一覧が変わっても利用日は動かない (データを取り出し直したわけではない)。ただし
  `scripts/push-data-repos.sh` は一覧の変化を中身の変化として扱い、その週を
  「確認 (差分なし)」とは書かない
- 相手先への不具合の連絡は、この仕組みの外に置く (第三者への発信なので、人が判断する)
