# 0002: CSV で台帳を取得し、詳細ページを巡回して統合する 2 段構えにする

## 状態

承認済み (2026-08-11)

## 文脈

2026-08-11 に実データベースへアクセスして取得方式を検証した
(実測の詳細は Issue #1 のコメント「調査所見: データ取得方式の実地検証」)。
判明した事実のうち、方式の選択に効いたものは次のとおり。

- CSV と詳細ページは**相補的**で、片方だけでは全項目が揃わない
  - CSV にしかない: 緯度・経度
  - 詳細ページにしかない: 解説文、構造及び形式等、員数、ふりがな、
    指定番号、創建及び沿革、重文指定基準ほか
- CSV の先頭 2 列 `(台帳ID, 管理対象ID)` が、そのまま詳細ページの
  URL `/heritage/detail/{台帳ID}/{管理対象ID}` になる。短い連番形式
  (`23`) と 8 桁ゼロ詰め形式 (`00003904`) が混在するが、いずれも
  同じ URL 形式で到達できることを確認した
- 検索一覧では複数棟の指定が `openRidgeList()` で 1:N に展開されるが、
  **CSV は最初から棟単位に展開済み**で、この 1:N を自前で解く必要がない
- CSV 出力 (`POST /utile/csv-list`) はサーバ側セッションと CSRF トークンに
  依存し、直前の検索条件に対して出力される。単独の URL では取得できない
- 詳細ページ (`GET /heritage/detail/...`) はセッション不要の静的な URL
- 素の HTTP クライアント (curl) で両方とも取得できた。ヘッドレスブラウザは不要
- 件数 (指定単位): 102 = 2,633 / 101 = 14,748 / 103 = 126
- CSV は UTF-8 (BOM 付き)・18 列・棟単位。Shift_JIS ではない

## 決定

次の 3 層に分けて実装する。リンクを辿る探索的なクロールは行わない。

1. **台帳取得層** — 分類 × 都道府県で検索して CSV を取得する。
   全件を一度に取ろうとしない (下記の分割方針を参照)
2. **詳細取得層** — 台帳の各行の `(台帳ID, 管理対象ID)` から詳細ページの
   URL を組み立てて取得する。検索や一覧の再現は不要
3. **統合層** — `(台帳ID, 管理対象ID)` をキーに 1:1 で結合する

### 分割方針

分割軸は**都道府県 (47) のみ**とする。分類 101 でも平均 314 件/県で、
種別・時代の軸まで使う必要がない。

なお 2,000 件の上限はトップページのお知らせ (2026/5/7) にあるとおり
システムメンテナンスに伴う**一時的な障害**であり、恒久的な仕様ではない。
障害が解消されても都道府県分割は維持する (1 リクエストあたりの応答時間と
失敗時の再取得範囲を小さく保てるため)。

### CSV 取得時の注意

CSV の POST パラメータは、**検索応答 HTML 内の csv-list フォームの
hidden 値をそのまま送る**こと。値を推測して組み立てると 504 Gateway
Timeout になる (調査中に実際に遭遇し、CSV 機能自体の障害と誤認しかけた)。

### アクセスマナー

利用規約にクローリングを禁じる記述はなく `robots.txt` も存在しないが、
明示的な許可もない。逐次アクセス・リクエスト間隔の挿入・User-Agent への
連絡先記載を自主的な制約として設ける。

## 影響

- 探索的なクロールが不要になり、取得対象は事前に台帳から確定できる。
  進捗の把握と再開が容易になる
- 詳細ページの取得は棟単位で 2 万件規模になる。毎回の全件取得は現実的で
  なく、**差分更新を前提とした設計**が必要になる (差分検出の方法は
  Issue #1 で継続議論)
- CSV 取得はセッションを維持する必要があるため、詳細取得 (ステートレス)
  とは実行単位を分けられる。失敗時の再試行範囲も別々に設計する
- 画像は取得・再配布の対象外とする
  ([0005](0005-private-until-license-confirmed.md))
