# 0008: 出力スキーマはキーを正規化し、詳細ページを正とする

## 状態

承認済み (2026-08-12)

## 文脈

[0004](0004-output-jsonl-per-prefecture.md) で出力形式を都道府県ごとの
JSON Lines と決めたが、**中身のスキーマは未決**のまま Issue #8 に残っていた。

2026-08-12 にキャッシュ済みの実データ (101 = 27 件 / 102 = 30 件 / 103 = 8 件) を
読んで、決定に効く事実が出揃った。

- **項目の集合が分類ごとに違う。** 102 にしかない項目 (棟名・構造及び形式等・
  創建及び沿革・国宝・重文区分)、103 にしかない項目 (面積) がある。103 には
  員数も所在都道府県も無い
- **同じ意味の項目が分類ごとに違う名前で出る。**
  指定番号 (102) / 登録番号 (101) / 告示番号 (103)、
  重文指定年月日 (102) / 登録年月日 (101) / 選定年月日 (103)、
  種別 (102) / 種別１・種別２ (101・103) など
- **CSV の列名は分類によって意味が変わる。** 101 の `重文指定年月日` 列には
  登録年月日が入り、102 の `種別1` 列には国宝・重文区分 (国宝 / 重要文化財) が
  入る。列名が同じでも中身は同じではない
- 日付の表記は CSV が `20041108`、詳細ページが `2004.11.08(平成16.11.08)` で
  一貫している。和暦は西暦の言い換えであり、独立した情報を持たない
- 附指定は詳細ページのモーダルに `附名称` と `附員数` の組で入っている
  (実データ 35 件すべてこの 2 項目)
- **所在都道府県が都道府県名でない行がある。** 101 の 3 件が `98` / `1` のまま
  (CSV も詳細ページも同じ値)。所在地の文字列は正しい

## 決定

### 1. キーは英数字に正規化し、原文ラベルとの対応表をコードに持つ

キーは英数字のスネークケースとする。分類ごとに違う原文ラベルでも、意味が同じ
なら同じキーへ寄せる。原文のままにすると、利用側が「登録番号か指定番号か告示
番号か」を分類で分岐して読むことになり、3 分類を 1 つのスキーマとして扱えない。

対応表の正本は `src/heritage_crawler/record.py` の `FIELD_KEYS`。決定時点の
対応は次のとおり (括弧内は出てくる分類)。

| 原文ラベル | キー |
|---|---|
| 名称 | `name` |
| ふりがな | `name_kana` |
| 棟名 (102) | `ridge_name` |
| 棟名ふりがな (102) | `ridge_name_kana` |
| 員数 (101・102) | `quantity` |
| 種別 (102) / 種別１・種別２ (101・103) | `types` (配列) |
| 時代 (101・102) | `period` |
| 年代 (101・102) | `year_text` |
| 西暦 (101・102) | `western_year` |
| 構造及び形式等 (101・102) | `structure` |
| 創建及び沿革 (102) | `history` |
| 棟礼、墨書、その他参考となるべき事項 (102) / その他参考となるべき事項 (101・103) | `notes` |
| 面積 (103) | `area` |
| 指定番号 (102) / 登録番号 (101) / 告示番号 (103) | `designation_number` |
| 登録回 (101) | `registration_round` |
| 国宝・重文区分 (102) | `national_treasure_class` |
| 重文指定年月日 (102) / 登録年月日 (101) / 選定年月日 (103) | `designated_date` |
| 登録告示年月日 (101) | `announced_date` |
| 国宝指定年月日 (102) | `national_treasure_date` |
| 追加年月日 | `added_date` |
| 重文指定基準 (102) / 登録基準 (101) / 選定基準 (103) の １〜３ | `criteria` (配列) |
| 所在都道府県 (101・102) | `prefecture` |
| 所在地 | `address` |
| 保管施設の名称 (101・102) | `storage_facility` |
| 所有者名 (101・102) | `owner` |
| 所有者種別 (101・102) | `owner_type` |
| 管理団体・管理責任者名 (101・102) | `custodian` |

指定・登録・選定は法的に別の行為なので、`designated_date` だけでは何の日付か
分からなくなる。分類から決まる `designation_kind` (`指定` / `登録` / `選定`) を
添えて自己記述的にする。

ページに無い項目は次のキーで補う。

- `ledger_id` / `managed_id` — 結合キー (ADR 0004 の並び順もこの 2 つ)
- `category_name` / `url` — 分類の表示名と詳細ページの URL
- `latitude` / `longitude` — CSV 由来 (下記 3)
- `description` (解説文) / `detailed_description` (詳細解説)
- `annexes` — 附指定 (下記 5)
- `has_attachment` / `has_photo` — 添付ファイルと写真の有無 (下記 5)

### 2. 日付は ISO 8601 に正規化し、和暦は残さない

`2004.11.08(平成16.11.08)` も `20041108` も `2004-11-08` にする。和暦は西暦の
言い換えでしかなく、二重に持つと差分が二重に出る。

正規化できない値はレコードに入れず、**件数と実例を報告する** (下記 7)。
黙って捨てない代わりに、型の揺れた値をデータへ流し込むこともしない。

### 3. 重複する項目は詳細ページを正とし、CSV からは緯度経度だけを採る

詳細ページは棟単位の一次表示であり、項目名と中身が対応している。対して CSV の
列は分類によって意味が変わる (文脈に挙げた 101 の `重文指定年月日` 列など)。
**列名が一致していても CSV の値は使わない。**

CSV から採るのは、CSV にしか無い**緯度・経度**だけとする (空のこともある)。
名称は突き合わせにのみ使い、食い違ったら報告する — 結合キーの取り違えは
名称のずれとして最初に現れるため。

### 4. 都道府県は詳細ページ → 所在地の順で決める

出力ファイルの振り分け (ADR 0004) に都道府県が要る。次の順で決める。

1. `所在都道府県` が 47 都道府県のいずれかならそれ
2. そうでなければ `所在地` の先頭に現れる都道府県名。ただし所在地に 2 つ以上の
   都道府県名が現れるなら `２県以上`
3. どちらでも決まらなければ `地域を定めない`

1 で決まらなかった件数は報告する。`98` / `1` のような未正規化の値
(`catalog.IRREGULAR_AREAS`) はここで所在地から拾い直され、元データが直れば
報告が 0 件になるだけで害はない。

### 5. 入れ子は附指定だけ配列にし、添付ファイルと写真は有無だけを持つ

- `annexes` — `[{"name": "棟札", "quantity": "6枚"}]`。附指定は 1 件の指定に
  複数ぶら下がり、名称と員数が対になっているので配列が素直
- `has_attachment` / `has_photo` — 真偽値。**画像とファイルの実体は扱わない**
  (ADR 0007)。有無はメタデータとして記録してよい

### 6. 欠損はキーごと落とす

値が空ならキーを出さない。`null` も空文字も使わない。分類によって項目集合が
違う以上「キーがある/無い」で分岐する読み方が必要になり、そこに「キーはあるが
空」を混ぜても区別が増えるだけで意味が増えない。JSON Lines の行も短くなる。

### 7. 取得時刻はレコードに入れない

取得のたびに全行が変わり、ADR 0004 の狙い (差分で「いつ何が変わったか」を読む)
を潰すため。出典表記と利用日はファイル・リポジトリ単位で示す (ADR 0007)。

### 8. 想定外を黙って捨てない

対応表に無いラベルが出たら、そのラベルと件数を報告する。サイト側に項目が
増えたことに気付ける唯一の場所がここになる。日付の正規化に失敗した値、
CSV と名称が食い違った件数、都道府県を所在地から決めた件数も同じ report に
出す。

## 影響

- 解析層は `src/heritage_crawler/detail_page.py` (HTML → 原文ラベルの辞書) と
  `src/heritage_crawler/record.py` (原文 → スキーマ) に分かれる。
  ラベルの読み取りとスキーマの決定を別々に差し替えられる
- スキーマの変更は出力データの破壊的変更になる。データリポジトリ側で
  スキーマのバージョンと変更履歴を示す (Issue #9)
- 解析はキャッシュ済み HTML だけを読む。スキーマを変えても 2 万件の再取得は
  要らない (ADR 0006)
- 和暦・CSV 由来の重複項目・取得時刻は出力に現れない。必要になったら
  キャッシュから作り直せる (どれも捨てているのは出力側だけ)
