# 0018: 月次の差分は台帳の突き合わせで見つけ、詳細は毎月 1/12 ずつ巡回する

## 状態

置換済み (2026-08-15)。[0020](0020-check-weekly-by-diffing-the-ledger-csv.md) が
週次に切り替え、突き合わせの基準を出力から前回の台帳 CSV へ移した。

**引き継がれた判断**: 前回の出力をデータリポジトリの JSON Lines から読むこと・
追加と削除を出力との突き合わせで決めること・網羅性が確かめられた分類でのみ落とす
こと・全件の組み立て直しはローカルに残すこと。

**覆った判断**: 実行の頻度 (月次 → 週次)・巡回の刻み (1/12 → 1/52)・台帳の値の
比較 (出力と比べる → 前回の CSV と比べる)・利用日 (実行日 → 取り出した日)。

## 文脈

初回の全件取得は 2026-08-12 に完走し、以降の差分更新は GitHub Actions の月次実行で
回す ([0006](0006-run-initial-crawl-locally-updates-on-actions.md))。Actions からの
疎通も確認できた (3 経路とも通り、エラーページ 0 件)。残るのは「何を取り直すか」で、
制約が 4 つある。

**1. ソース側に更新日が無い。** 4 分類のキャッシュ済み詳細ページを実測したが、
更新日・改定日に当たる記述が 1 つも無い。CSV にも無い
(`ledger.EXPECTED_CSV_HEADER` は台帳ID から経度までの 18 列)。**いつ変わったかを
ソースから知る術がない。**

**2. 変更が台帳に出るかどうかは項目で違う。**

| 変更 | 台帳 (CSV) に出るか |
|---|---|
| 新規指定・指定解除 | 出る (行の有無) |
| 名称・所在地・都道府県・緯度経度・時代・種別 | 出る |
| 解説文・員数・構造及び形式等・附指定・措置の履歴 | **出ない** (詳細ページだけの項目) |

**3. 全件の取り直しは月次に載らない。** 23,742 件 / 1 req/s で約 6.6 時間。Actions の
ジョブ上限はちょうど 6 時間。公共サイトへ毎月 2.4 万リクエストを投げること自体、
[0002](0002-two-stage-fetch-csv-then-detail.md) のアクセスマナーに照らして重い。

**4. Actions には「前回の状態」を置く場所が無い。** Actions のキャッシュは 7 日で
エビクトされるので月次では毎回空。生 HTML (gzip で約 270 MB) はリポジトリに
コミットしない ([0006](0006-run-initial-crawl-locally-updates-on-actions.md))。

一方、**前回の状態はすでにデータリポジトリにある**。10 リポジトリの JSON Lines に
23,742 件が入っていて、`(台帳ID, 管理対象ID)` で引ける。書き出しているのは
`record.build_record` の出力そのままなので、読み戻せばレコードとして再利用できる。

## 決定

- **「前回の状態」の正本はデータリポジトリの JSON Lines。** キャッシュも生 HTML も
  Actions へ持ち回らない。差分更新は 10 リポジトリを clone して既存の行を読み、
  取り直したぶんで差し替える
- **台帳は毎月まるごと取り直す** (204 リクエスト)。追加・削除・台帳に出る変更は
  すべてここから出る。あわせて `audit-listing` も回して網羅性を確かめる
  ([0017](0017-audit-completeness-with-the-search-listing.md))
- **詳細ページを取り直すのは 3 種類だけ。**
  1. 台帳に現れた新しいキー (新規指定)
  2. 台帳の値が前回と変わったキー
  3. **巡回のぶん — 全体の 1/12。** `(台帳ID, 管理対象ID)` のハッシュを 12 で割った
     余りが実行月に一致するものを取る。決定的で、都道府県にも種別にも偏らない
- **消えたキーは JSON Lines から削除する** (指定解除)。ただし**その分類の網羅性の
  突き合わせが通っていることを条件にする** — 取得の失敗や相手側の一時的な障害を
  指定解除と誤認して行を消さないため
- **データが変わらない月は JSON Lines を 1 行も動かさない。** 生成物は決定的なので
  ([0014](0014-machine-readable-dataset-metadata.md))、データが変わらなければ
  同じバイト列が出る。**ただし `meta.json` の利用日は毎月動く** (下記) ので、
  その月のコミットはその 1 ファイルだけになる。**「確認しただけの月」と
  「データが変わった月」はコミットメッセージで見分けられるようにする** —
  履歴を見て実際の変更だけを追えなくなるのを避けるため
- **`meta.json` の利用日は実行日 (日本時間) にする。** 全件取得では
  `DetailEntry.fetched_at` の最大値を使うが ([0014](0014-machine-readable-dataset-metadata.md))、
  差分更新では既存レコードの取得日を知る術がない。そもそも利用日は「いつ
  データベースを利用したか」なので、台帳を全件取り直している月次実行では実行日が正しい
- **全件を相手にする操作はローカルに残す。** スキーマを変えたとき・キャッシュの
  パース仕様を変えたときの全件再組み立ては、270 MB のキャッシュがあるローカルで
  行って push する。Actions は差分専用にする — [0006](0006-run-initial-crawl-locally-updates-on-actions.md)
  で決めた分担 (初回はローカル / 差分は Actions) をそのまま延長する

## 影響

- 月次実行の所要は約 70 分 (台帳 204 リクエスト + 巡回 約 2,000 件 + 新規・変更ぶん)。
  ジョブ上限 6 時間に対して余裕があり、無料枠 2,000 分の 3.5% で収まる。
  **都道府県マトリクスを使わないので `max-parallel: 1` の論点自体が消える** —
  単一ジョブが逐次に取るので、レート上限は `RateLimiter` が守る
  ([0010](0010-rate-limit-by-request-start.md))
- **詳細ページだけの変更が反映されるまで最長 12 ヶ月かかる。** 毎月の負荷を一定に
  する代償で、これは意図した妥協。急ぐときは巡回の割り当てを手で指定して走らせる
- 巡回は毎月おおよそ 2,000 件を取り直すが、**変わっていなければ JSON Lines に差分は
  立たない** (生成物が決定的なため)。git の履歴に出るのは実際に中身が変わった行だけ
- **10 リポジトリに毎月 1 つずつコミットが立つ** (`meta.json` の利用日が動くため。
  年 120 コミット)。実測で確かめた — データを変えずに月だけ進めると、JSON Lines
  405 ファイルは 1 バイトも動かず、変わるのは `meta.json` 10 個の `accessed_date`
  と出典表記だけだった。**利用日は「実際にデータベースへアクセスした日」なので
  動くのが正しく**、毎月確認した証跡にもなる
- clone するのは 10 のデータリポジトリ。JSON Lines は合計で数十 MB なので、
  `--depth 1` なら 1 分もかからない。push には PAT か GitHub App が要る
  (別リポジトリのため)
- キャッシュを Actions へ持ち込まないので、**差分更新の実行後もローカルの
  キャッシュは古いまま**になる。ローカルで全件再組み立てをするときは、先に
  `fetch-ledger` と `fetch-detail` を回して手元を追いつかせる必要がある
- 台帳の突き合わせは前回の台帳ではなく**既存の JSON Lines と行う**。前回の CSV を
  どこにも保存しないで済み、比較の基準が出力そのものになる (出力と基準がずれない)
- **どの列で比べるかは実装時に実測して決めた** (Issue #10 のコメント)。JSON Lines に
  入っているのは詳細ページ由来の値なので (CSV から採るのは緯度経度だけ)、同じ意味の
  欄でも一致するとは限らない。23,742 件で測って 99.9% 以上一致した列 — 名称・棟名・
  所在地・所有者名・時代・種別・緯度経度 — だけを使う。**都道府県は使えない**
  (出力側は正規化済みで `２県以上` は値を持たない) が、所在地の比較で足りる
