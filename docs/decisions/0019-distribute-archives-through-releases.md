# 0019: 配布物は GitHub Releases で配り、差分はリリースどうしの突き合わせで出す

## 状態

承認済み (2026-08-14)

## 文脈

データは 10 のリポジトリへ出力され ([0009](0009-output-to-existing-per-type-repositories.md) /
[0012](0012-crawl-monuments-and-route-by-kind.md))、閲覧サイトも立った
([0015](0015-single-cross-type-site-on-pages.md))。しかし**まとめて落とす手段と、
版を固定して引用する手段が無い**。

- データを全部欲しい人は 10 リポジトリを `git clone` して回る
- サイトが配信している JSON Lines は 1 ファイルずつしか取れず、版も固定されない
- 「2026 年 9 月時点のデータ」を指して引用できない

**何が変わったかも読めない。** 月次のコミットメッセージは
`chore(data): 2026-09 の差分を反映` / `... に確認 (データの変更なし)` の 2 種類
だけで ([0018](0018-detect-monthly-changes-with-the-ledger-and-a-rotation.md))、
どの文化財が追加・解除されたかは JSON Lines の diff を自分で読むしかない。
新規指定・指定解除はこのデータで最も知りたい出来事なのに、そこへ辿り着く道が
git の履歴しかない。

規模は配布の妨げにならない。全 JSON Lines を ZIP にして **7.1 MB** (実測)。
リリースのアセットは 1 つ 2 GB まで置ける。

差分の出どころには 3 つの候補があった。

**(A) クローラーの月次の計画を使う。** `update-records` は「なぜ取り直すか」
(新規 / 台帳の値が変わった / 巡回) を持っている。しかし**あれは台帳ベース**で、
解説文・員数・構造及び形式等のような**詳細ページにしかない項目の変更が現れない**
([0018](0018-detect-monthly-changes-with-the-ledger-and-a-rotation.md) が
「台帳に出るか」で表にしたとおり)。巡回で取り直して初めて分かる差なので、
計画を履歴にすると毎月取りこぼす。

**(B) データリポジトリの git 履歴を使う。** サイトのビルドは `--depth 1` で
clone しており、前回の状態を持っていない。深く clone すれば取れるが、月次以外の
手直しが挟まった月に「前回のリリース以降」と一致しなくなる。

**(C) 配布物どうしを比べる。** 前回のリリースの ZIP と今回のデータを突き合わせる。
「配って以降に変わったもの」がそのまま出て、意味も正しい。

## 決定

**GitHub Releases で ZIP を配り、リリースノートに変更内容を書く。**

- **配布物は 11 個。** 種別横断の全部入り (`heritages-jsonl.zip`) を
  `code4heritage/heritages` のリリースへ、種別ごとの `<リポジトリ名>-jsonl.zip` を
  **各データリポジトリのリリース**へ置く。**中身の構造は置き場に合わせる** —
  全部入りはリポジトリ名で仕切り、種別ごとのぶんは展開するとそのデータリポジトリの
  中身になる
- **作るのは heritages のワークフロー 1 つ。** データリポジトリごとに複製しない
  ([0001](0001-split-repositories-by-heritage-type.md) の「分けるのはデータで
  あってコードではない」)。クローラー側にも置かない — **差分の計算とノートの生成が
  2 箇所に分かれると二重管理になる**。heritages は配信のために既に 10 リポジトリを
  clone しており、配るのはその延長にある
- **差分は (C) で出す。** 前回のリリースの ZIP を落として突き合わせる。比較の
  キーは **`(データセット, 台帳ID, 管理対象ID)`** — データセットを含めないと、
  複合指定 (同じ棟が複数の種別に現れる。114 件。
  [0012](0012-crawl-monuments-and-route-by-kind.md)) が種別をまたいで動いたときに
  「変更なし」に化ける
- **前回の状態は全部入り 1 つで足りる。** 種別ごとのリリースを個別に取りに
  行かない。10 回同じ突き合わせをすることになるうえ、どれか 1 つが取れなかった月に
  基準がばらける
- **差分のある種別だけリリースを作る。** `meta.json` の利用日は毎月動くが
  ([0018](0018-detect-monthly-changes-with-the-ledger-and-a-rotation.md))、
  見ているのは行の中身なので、データが変わらなかった月はどこにもリリースが立たない
- **アセット名は月ごとに変えない。** `releases/latest/download/<名前>` を固定 URL
  として使えるようにする。版はタグ (`data-YYYY-MM-DD`) が持つ。データセットに
  SemVer は当てはまらない
- **ZIP は決定的に作る。** 格納順とタイムスタンプを固定し、目録に生成日時を
  入れない。[0014](0014-machine-readable-dataset-metadata.md) が生成物に持たせた
  性質を配布物まで延ばす
- **リリースノートには全量を入れない。** ノートは 125,000 字が上限で、スキーマを
  変えて全件を組み立て直した月には 2 万件が動きうる。本文は件数と抜粋にとどめ、
  全量は `changes.md` / `changes.json` をアセットとして添える
- **配信を止める不変条件を、そのまま「配ってよいか」の判定に使う。** 壊れたデータを
  固めて配ると、あとから取り消せない

## 影響

- **クローラーは変わらない。** 月次の差分更新はこれまでどおりデータリポジトリへ
  push するだけで、配布はその翌日に heritages 側で走る
- `code4heritage/heritages` に**クローラーの月次更新と同じ GitHub App** の secret
  (`DATA_PUSH_CLIENT_ID` / `DATA_PUSH_PRIVATE_KEY`) が要る。データリポジトリへ
  リリースを作るため。**無いときは相手先へ出る前に落とす** — 全部入りだけ配られて
  10 個が揃わない状態を作らない
- リリースが履歴になるので、**CHANGELOG.md はどこにもコミットしない**。
  [0015](0015-single-cross-type-site-on-pages.md) の「生成物はコミットしない」を
  保ち、heritages に毎月の自動コミットも立たない
- 種別ごとのリリースは、そのリポジトリの読み手にとって「落として展開すれば中身が
  出る」形になる。データリポジトリを clone しなくても使える
- 詳細ページだけの変更は巡回で見つかるため、リリースノートに載るまで最長 12 ヶ月
  かかる ([0018](0018-detect-monthly-changes-with-the-ledger-and-a-rotation.md) の
  妥協がそのまま届く)。**変更として現れないのではなく、現れるのが遅い**
- 配布物の合計は毎月 14 MB ほど増える (全部入り 7.1 MB + 種別ごとの合計)。
  リリースのアセットは容量無制限で、リポジトリの大きさにも算入されない
